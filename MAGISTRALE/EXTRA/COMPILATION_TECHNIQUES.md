# LinguaggiI

![[Pasted image 20260707152159.png]]

The length of a string x, denoted by |x|, is the number of symbols which compose x

The concatenation of two strings x and y is a string xy. It is an associative operation that admits the neutral element ε

s is a substring of x if there exist two strings y and z such that x = ysz:
- choosing y=ε, x=sz, then s is called a prefix of x;
- choosing z=ε, x=ys, then s is called a suffix of x;

ε is a prefix and a suffix of any string (including ε itself)

We define the set of all strings over Σ of a given length.

$\Sigma^n$ denotes the strings on Σ whose length is n

![[Pasted image 20260707152634.png]]

A language L is a set of strings over an alphabet: $L \subseteq \Sigma^*$ is a language over $\Sigma$

Operations on Languages:
- Union $A \cup B$
- Intersection $A \cap B$
- Difference A\B (when $B \subseteq A$)
- Complement $\overline{A} = \Sigma^* - A$ where $\Sigma^*$ is the set of all strings on $\Sigma$
- Concatenation $AB = \{ab \;|\; a \in A \; and \; b \in B\}$
- Kleene CLosure $A^* = \bigcup_{i=0}^\infty A^i$
- $A^+ = \bigcup_{i=1}^\infty A^i$

$\emptyset \not= \{\epsilon\}$

Starting from a particular initial symbol, using the rewriting rules of the productions, we generate the set of all the strings belonging to the language

Grammar $G=(\Sigma, N, S, P)$:
- $\Sigma$ is the alphabet, a set of symbols (terminals)
- N is the set of non terminals
- $S \in N$ is the starting symbol
- P is the set of productions $U \to V$:
	- $U \in (\Sigma \cup N)^+$
	- $V \in (\Sigma \cup N)^*$

A string $w \in \Sigma^*$ is generated by G if there exists a derivation starting from S and resulting in w obtained by rewriting the string using the productions in P

A language generated by grammar G is denoted L(G) and it is the set of strings derived using G.

## Deterministic Finite Automata:
- $(Q,\Sigma,\delta,q_0,F)$
	- Q a finite set of states
	- $\Sigma$ a finite set of symbols
	- $\delta:Q \times \Sigma \to Q$ the transition function takes as argument a state and a symbol and returns one state
	- $q_0 \in Q$ the starting set
	- $F \subseteq Q$ the set of final or accepting states

## Regular Grammars <-> NFA
### RG -> NFA

![[Pasted image 20260707160949.png]]

#### Example

![[Pasted image 20260729162630.png]]
##### **Step 1: States ($Q$)**

- Create a state for each non-terminal symbol: $q_S$ and $q_B$.
- Add a special final state $q_f$. 
  $$\mathbf{Q = \{q_S, q_B, q_f\}}$$

##### **Step 2: Start State ($q_0$)**

- The start state corresponds to the grammar's start symbol $S$:  $$\mathbf{q_0 = q_S}$$

##### **Step 3: Accepting / Final States ($F$)**

- The special state $q_f$ is an accepting state.
- Since there are no $\varepsilon$-productions ($A \to \varepsilon$), no other state is an accepting state.
  $$\mathbf{F = \{q_f\}}$$
##### **Step 4: Transition Function ($\delta$)**

Map each production rule to a transition:

1. **Rule $S \to aS$** (Form $A \to aB$):
    - $\delta(q_S, a) \ni q_S$ 
2. **Rule $S \to aB$** (Form $A \to aB$):
    - $\delta(q_S, a) \ni q_B$ 
3. **Rule $B \to bB$** (Form $A \to aB$):
    - $\delta(q_B, b) \ni q_B$
4. **Rule $B \to b$** (Form $A \to a$):
    - $\delta(q_B, b) \ni q_f$

Combined transition function $\delta$:

- $\delta(q_S, a) = \{q_S, q_B\}$
- $\delta(q_S, b) = \emptyset$
- $\delta(q_B, a) = \emptyset$
- $\delta(q_B, b) = \{q_B, q_f\}$
- $\delta(q_f, a) = \emptyset$
- $\delta(q_f, b) = \emptyset$
##### NFA Definition

The formal NFA $M = (Q, \Sigma, \delta, q_0, F)$ is:

- $Q = \{q_S, q_B, q_f\}$
    
- $\Sigma = \{a, b\}$
    
- $q_0 = q_S$
    
- $F = \{q_f\}$
    

##### **Transition Table**

|**State**|**Input a**|**Input b**|
|---|---|---|
|**$\rightarrow q_S$** (Start)|$\{q_S, q_B\}$|$\emptyset$|
|**$q_B$**|$\emptyset$|$\{q_B, q_f\}$|
|**$*q_f$** (Final)|$\emptyset$|$\emptyset$|


### NFA -> RG

![[Pasted image 20260707161834.png]]

![[Pasted image 20260707162433.png]]

#### 1. Mapping States to Non-Terminals ($N$)

Map each state of the NFA to a non-terminal symbol:

- $q_0 \implies A_0$ (Start Symbol $S$)
    
- $q_1 \implies A_1$
    
- $q_2 \implies A_2$
    
- **Alphabet ($\Sigma$):** $\{0, 1\}$
    
- **Non-terminals ($N$):** $\{A_0, A_1, A_2\}$
    
- **Start Symbol ($S$):** $A_0$
    

#### 2. Method 1: Standard Scheme (with $\varepsilon$-productions)

##### **A. Transitions $\to$ Rules ($A_i \to a A_j$)**

- **From State $q_0$ ($A_0$):**
    
    - $\delta(q_0, 0) = \{q_0\} \implies A_0 \to 0 A_0$
        
    - $\delta(q_0, 1) = \{q_0, q_1\} \implies A_0 \to 1 A_0 \mid 1 A_1$
        
- **From State $q_1$ ($A_1$):**
    
    - $\delta(q_1, 0) = \{q_1\} \implies A_1 \to 0 A_1$
        
    - $\delta(q_1, 1) = \{q_0, q_2\} \implies A_1 \to 1 A_0 \mid 1 A_2$
        
- **From State $q_2$ ($A_2$):**
    
    - $\delta(q_2, 0) = \{q_1, q_2\} \implies A_2 \to 0 A_1 \mid 0 A_2$
        
    - $\delta(q_2, 1) = \{q_0, q_1, q_2\} \implies A_2 \to 1 A_0 \mid 1 A_1 \mid 1 A_2$
        

##### **B. Final States $\to \varepsilon$-productions**

Since $F = \{q_2\}$, add the termination rule for $A_2$:
- $A_2 \to \varepsilon$
##### **Resulting Production Rules ($P$):**

$$A_0 \to 0 A_0 \mid 1 A_0 \mid 1 A_1$$

$$A_1 \to 0 A_1 \mid 1 A_0 \mid 1 A_2$$

$$A_2 \to 0 A_1 \mid 0 A_2 \mid 1 A_0 \mid 1 A_1 \mid 1 A_2 \mid \varepsilon$$

#### 3. Method 2: Direct Scheme (without $\varepsilon$-productions)

If you prefer to eliminate $\varepsilon$-productions, add terminal-only rules whenever a transition targets an accepting state ($q_2 \in F$):

- For transition $A_1 \xrightarrow{1} A_2$ (where $q_2 \in F$): add $A_1 \to 1$
    
- For transition $A_2 \xrightarrow{0} A_2$ (where $q_2 \in F$): add $A_2 \to 0$
    
- For transition $A_2 \xrightarrow{1} A_2$ (where $q_2 \in F$): add $A_2 \to 1$
    

##### **Resulting Production Rules ($P$):**

$$A_0 \to 0 A_0 \mid 1 A_0 \mid 1 A_1$$

$$A_1 \to 0 A_1 \mid 1 A_0 \mid 1 A_2 \mid 1$$

$$A_2 \to 0 A_1 \mid 0 A_2 \mid 1 A_0 \mid 1 A_1 \mid 1 A_2 \mid 0 \mid 1$$
## NFA -> DFA

The NFA are usually easier to design. For each NFA N there is a DFA D, such that L (D) = L (N). This involves a subset construction.

Given an NFA $N = (Q_N,\Sigma,\delta_N,q_0,F_N)$
we will build a DFA $D = (Q_D,\Sigma,\delta_D,q_0,F_D)$
such that $L(D) = L(N)$

$Q_D = \wp(Q_N)$

Note that not all these state are necessary, most of them will be unreachable.

$\forall P \in \wp(Q_N): \; \delta_D(P,a)=\bigcup_{p \in P} \delta_N(p,a)$

$F_D = \{P \in \wp(Q_N)\;|\; P \cap F_N \not = \emptyset\}$

Lexical Analyzer, a.k.a. lexer, scanner or tokenizer, splits the input program, seen as a stream of characters, into a sequence of tokens.

Tokens are the words of the (programming) language, e.g., keywords, numbers, comments, parenthesis, semicolon.

Tokens are classes of concrete input (called lexeme).

analysis is the very first phase in the compiler designing, the only one that analyses the entire code

A lexeme is a sequence of characters that are included in the source program according to the matching pattern of a token

Lexical analyzer helps to identify token into the symbol table

A character sequence which is not possible to scan into any valid token is a lexical error

*By hand* - Identify lexemes in input and return tokens

*Automatically* - Lexical-Analyser generator: it compiles the patterns that specify the lexemes into a code (the lexical analyser).

Lexical analysis decides whether the individual tokens are well formed, this can be expressed by a regular language.

```ocaml
(*
 * Hand-written lexer for a simple assignment language, e.g.:
 *      sum = a1 + 23 - value2
 *
 * Grammar of tokens:
 *      IDENTIFIER -> [a-zA-Z][a-zA-Z0-9]*
 *      NUMBER     -> [0-9]+
 *      ASSIGN     -> '='
 *      PLUS       -> '+'
 *      MINUS      -> '-'
 *      EOF        -> end of input
 *
 * Whitespace (space, tab, newline) is skipped.
 * Any other character triggers a lexical error.
 *
 * Compile:  ocamlfind ocamlopt -package str -linkpkg -o lexer lexer.ml
 *   (or just: ocaml lexer.ml)
 * Run:      ./lexer
 *)

(* ---------- Token definition ---------- *)

type token_type =
  | IDENTIFIER of string
  | NUMBER of string
  | ASSIGN
  | PLUS
  | MINUS
  | EOF
  | ERROR of char

let token_type_name = function
  | IDENTIFIER _ -> "IDENTIFIER"
  | NUMBER _     -> "NUMBER"
  | ASSIGN       -> "ASSIGN"
  | PLUS         -> "PLUS"
  | MINUS        -> "MINUS"
  | EOF          -> "EOF"
  | ERROR _      -> "ERROR"

(* ---------- Lexer state ---------- *)

type lexer = {
  src : string;
  len : int;
  mutable pos : int;   (* index of the current (lookahead) character *)
  mutable line : int;  (* current line number, for error messages *)
}

let lexer_init src =
  { src; len = String.length src; pos = 0; line = 1 }

(* current character under the lookahead, without consuming it.
   returns '\000' at end of input, used as a sentinel. *)
let peek lx = if lx.pos >= lx.len then '\000' else lx.src.[lx.pos]

(* consume and return the current character, advancing the lookahead *)
let advance lx =
  let c = peek lx in
  if c <> '\000' then 
  begin
    lx.pos <- lx.pos + 1;
    if c = '\n' then lx.line <- lx.line + 1
  end;
  c

let is_alpha c = (c >= 'a' && c <= 'z') || (c >= 'A' && c <= 'Z')
let is_digit c = c >= '0' && c <= '9'
let is_alnum c = is_alpha c || is_digit c

(* ---------- Step 1: skip whitespace ---------- *)

let rec skip_whitespace lx =
  match peek lx with
  | ' ' | '\t' | '\n' -> ignore (advance lx); skip_whitespace lx
  | _ -> ()

(* ---------- Core: NEXT_TOKEN() ---------- *)

let next_token lx : token_type =
  (* Step 1: skip any whitespace *)
  skip_whitespace lx;

  (* Step 2: inspect the current character (lookahead) *)
  let c = peek lx in

  (* Step 5 (EOF case): end of input *)
  if c = '\000' then EOF

  (* Step 3/4: recognize the longest valid token and consume it *)

  (* IDENTIFIER: letter followed by letters/digits *)
  else if is_alpha c then 
  begin
    let buf = Buffer.create 16 in
    while is_alnum (peek lx) do
      Buffer.add_char buf (advance lx)
    done;
    IDENTIFIER (Buffer.contents buf)
  end

  (* NUMBER: one or more digits *)
  else if is_digit c then 
  begin
    let buf = Buffer.create 16 in
    while is_digit (peek lx) do
      Buffer.add_char buf (advance lx)
    done;
    NUMBER (Buffer.contents buf)
  end

  (* Single-character operators *)
  else if c = '=' then (ignore (advance lx); ASSIGN)
  else if c = '+' then (ignore (advance lx); PLUS)
  else if c = '-' then (ignore (advance lx); MINUS)

  (* Invalid character: lexical error. Consume it so we don't loop forever. *)
  else 
  begin
    ignore (advance lx);
    ERROR c
  end

(* ---------- Driver ---------- *)

let () =
  let input = "x = 10 + y" in
  Printf.printf "Input: \"%s\"\n\n" input;
  Printf.printf "Output tokens:\n";

  let lx = lexer_init input in

  let rec loop () =
    let tok = next_token lx in
    (match tok with
     | ERROR c ->
       Printf.eprintf "Lexical error at line %d: unexpected character '%c'\n" lx.line c
     | IDENTIFIER s | NUMBER s -> Printf.printf "%s(%s)\n" (token_type_name tok) s
     | _ -> Printf.printf "%s\n" (token_type_name tok));
    if tok <> EOF then loop ()
  in
  loop ()
```

### Step 1 — FIRST sets

No production derives ε, so this is straightforward (just take the first terminal(s) of each RHS).

|Non-terminal|Productions|FIRST|
|---|---|---|
|A|ab \| c|{a, c}|
|B|dC|{d}|
|C|eC \| g|{e, g}|
|D|fD \| g|{f, g}|
|S|AB \| eDa|{a, c, e}|

(FIRST(S): from `AB`, since A doesn't derive ε, FIRST(AB) = FIRST(A) = {a, c}. From `eDa`, FIRST = {e}.)

### Step 2 — FOLLOW sets

- **FOLLOW(S)** = {$} — start symbol.
- **FOLLOW(A)**: A appears only in `S → AB`, immediately followed by B → FOLLOW(A) = FIRST(B) = **{d}**.
- **FOLLOW(B)**: B appears only in `S → AB`, at the end → FOLLOW(B) = FOLLOW(S) = **{$}**.
- **FOLLOW(C)**: C appears in `B → dC` (end of B → add FOLLOW(B)) and in `C → eC` (end, self-recursive, adds nothing new) → FOLLOW(C) = **{$}**.
- **FOLLOW(D)**: D appears in `S → eDa`, followed by terminal `a` → FOLLOW(D) = **{a}**. (Also in `D → fD`, self-recursive, adds nothing new.)

### Step 3 — Parsing table

For each production `X → α`, place it in column _t_ for every `t ∈ FIRST(α)` (no ε cases here, so FOLLOW is never needed for placement — the FOLLOW sets above were only intermediate work, except none of them end up needed since no nullable productions exist).

| Non-terminal | a    | b   | c    | d    | e     | f    | g   | $   |
| ------------ | ---- | --- | ---- | ---- | ----- | ---- | --- | --- |
| S            | S→AB |     | S→AB |      | S→eDa |      |     |     |
| A            | A→ab |     | A→c  |      |       |      |     |     |
| B            |      |     |      | B→dC |       |      |     |     |
| C            |      |     |      |      | C→eC  |      | C→g |     |
| D            |      |     |      |      |       | D→fD | D→g |     |

Every filled cell has exactly **one** production — no cell has two — so this grammar is **LL(1)**, and a table-driven descendent (predictive) parser can be built directly from it.

**How to read/use it:** the parser keeps a stack starting with `S` and `$`. At each step, look at the top-of-stack non-terminal and the current input token, find the entry in the table, and replace the non-terminal with the RHS (pushed in reverse). Terminals on the stack must match the input directly and are popped/consumed.

For example, parsing `c d e g $` (i.e. `A=c`, `B=dC`, `C=eC`, then `C=g`):

1. Stack `S$`, input `c` → M\[S,c] = S→AB → stack `AB$`
2. Top `A`, input `c` → M\[A,c] = A→c → stack `cB$`
3. Match `c`, consume → stack `B$`, input `d`
4. Top `B`, input `d` → M\[B,d] = B→dC → stack `dC$`
5. Match `d`, consume → stack `C$`, input `e`
6. Top `C`, input `e` → M\[C,e] = C→eC → stack `eC$`
7. Match `e`, consume → stack `C$`, input `g`
8. Top `C`, input `g` → M\[C,g] = C→g → stack `g$`
9. Match `g`, consume → stack `$`, input `$` → **accept**.

### 2) 
![[Pasted image 20260709155446.png]]

To construct the descendent LL(1) parsing table for the given grammar, we need to follow a systematic three-step process:

1. Determine the **FIRST** sets for each non-terminal.
2. Determine the **FOLLOW** sets for each non-terminal.
3. Use these sets to construct the rows and columns of the parsing table.
#### Step 1: Compute the FIRST Sets

The **FIRST** set of a string of symbols is the set of terminals that can appear as the first symbol of a string derived from it (plus $\epsilon$ if the string can derive the empty string).

- **$FIRST(F)$**: From $F \rightarrow (E)$ and $F \rightarrow \text{id}$ 
$$FIRST(F) = \{ \text{(}, \text{id} \}$$
- **$FIRST(G)$**: From $G \rightarrow + FG$ and $G \rightarrow \epsilon$
$$FIRST(G) = \{ \text{+}, \epsilon \}$$
- **$FIRST(E)$**: Since $E \rightarrow FG$, it inherits the first terminals of $F$:
$$FIRST(E) = FIRST(F) = \{ \text{(}, \text{id} \}$$
- **$FIRST(S)$**: From the three alternatives of $S$:
$$FIRST(S) = \{ \text{id}, \text{read}, \text{write} \}$$ 
- **$FIRST(T)$**: From $T \rightarrow ST$ and $T \rightarrow \epsilon$:
$$FIRST(T) = FIRST(S) \cup \{ \epsilon \} = \{ \text{id}, \text{read}, \text{write}, \epsilon \}$$
- **$FIRST(L)$**: Since $L \rightarrow ST$ and $S$ is not nullable:
$$FIRST(L) = FIRST(S) = \{ \text{id}, \text{read}, \text{write} \}$$
- **$FIRST(P)$**: From $P \rightarrow \text{begin } L \text{ end}$:
$$FIRST(P) = \{ \text{begin} \}$$

#### Step 2: Compute the FOLLOW Sets

The **FOLLOW** set of a non-terminal $A$ is the set of terminals that can appear immediately to the right of $A$ in some sentential form. $\$$ denotes the end-of-input marker.

- **$FOLLOW(P)$**: As the start symbol:
$$FOLLOW(P) = \{ \$ \}$$
- **$FOLLOW(L)$**: From $P \rightarrow \text{begin } L \text{ end}$:
$$FOLLOW(L) = \{ \text{end} \}$$
- **$FOLLOW(T)$**: From $L \rightarrow ST$ and $T \rightarrow ST$, $T$ is at the very end of these productions, so it inherits from $L$ and itself:
$$FOLLOW(T) = FOLLOW(L) = \{ \text{end} \}$$
- **$FOLLOW(S)$**: From $L \rightarrow ST$ and $T \rightarrow ST$: $S$ is followed by $T$. Therefore, $FOLLOW(S)$ contains $FIRST(T) \setminus \{\epsilon\}$. Because $T$ can be $\epsilon$, $FOLLOW(S)$ also contains $FOLLOW(L)$ and $FOLLOW(T)$:
$$FOLLOW(S) = \{ \text{id}, \text{read}, \text{write}, \text{end} \}$$
- **$FOLLOW(E)$**: From $S \rightarrow \text{id } := E ;$, $S \rightarrow \text{write } (E) ;$, and $F \rightarrow (E)$:
$$FOLLOW(E) = \{ \text{;}, \text{)} \}$$
- **$FOLLOW(G)$**: From $E \rightarrow FG$ and $G \rightarrow + FG$, $G$ is at the right end, so it inherits from $E$:
$$FOLLOW(G) = FOLLOW(E) = \{ \text{;}, \text{)} \}$$
- **$FOLLOW(F)$**: From $E \rightarrow FG$ and $G \rightarrow + FG$: $F$ is followed by $G$. Thus, $FOLLOW(F)$ contains $FIRST(G) \setminus \{\epsilon\} = \{+\}$. Since $G$ is nullable, it also contains $FOLLOW(E)$ and $FOLLOW(G)$:
$$FOLLOW(F) = \{ \text{+}, \text{;}, \text{)} \}$$

#### Step 3: Construct the LL(1) Parsing Table

To fill each cell `TABLE[A, a]` where `A` is a non-terminal and `a` is a terminal:

1. Add the production $A \rightarrow \alpha$ to `TABLE[A, a]` for each terminal $a \in FIRST(\alpha)$.
2. If $\epsilon \in FIRST(\alpha)$, add $A \rightarrow \alpha$ to `TABLE[A, b]` for each terminal $b \in FOLLOW(A)$.

All empty cells signify syntax errors.

| **Non-Terminal** | **begin**                                   | **end**                  | **id**                            | **:=** | **;**                    | **read**                           | **(**               | **)**                    | **write**                          | **+**                | **$** |
| ---------------- | ------------------------------------------- | ------------------------ | --------------------------------- | ------ | ------------------------ | ---------------------------------- | ------------------- | ------------------------ | ---------------------------------- | -------------------- | ----- |
| **P**            | $P \rightarrow \text{begin } L \text{ end}$ |                          |                                   |        |                          |                                    |                     |                          |                                    |                      |       |
| **L**            |                                             |                          | $L \rightarrow ST$                |        |                          | $L \rightarrow ST$                 |                     |                          | $L \rightarrow ST$                 |                      |       |
| **T**            |                                             | $T \rightarrow \epsilon$ | $T \rightarrow ST$                |        |                          | $T \rightarrow ST$                 |                     |                          | $T \rightarrow ST$                 |                      |       |
| **S**            |                                             |                          | $S \rightarrow \text{id } := E ;$ |        |                          | $S \rightarrow \text{read } (id);$ |                     |                          | $S \rightarrow \text{write } (E);$ |                      |       |
| **E**            |                                             |                          | $E \rightarrow FG$                |        |                          |                                    | $E \rightarrow FG$  |                          |                                    |                      |       |
| **G**            |                                             |                          |                                   |        | $G \rightarrow \epsilon$ |                                    |                     | $G \rightarrow \epsilon$ |                                    | $G \rightarrow + FG$ |       |
| **F**            |                                             |                          | $F \rightarrow \text{id}$         |        |                          |                                    | $F \rightarrow (E)$ |                          |                                    |                      |       |

# PRESENTATION

## Slide 1

Good morning everyone. Today I am going to present the paper **"Finding and Understanding Bugs in C Compilers,"** a seminal piece of research conducted at the University of Utah. This study details the creation and results of **Csmith**, a tool designed to stress-test compilers and uncover defects that traditional testing methods often miss.

## Slide 2

We must first ask: why does **compiler correctness** matter so much? The C programming language is at the very core of our modern computing infrastructure. It is the foundation for mission-critical financial servers, life-critical medical devices like pacemakers, and the fly-by-wire software used in Airbus aircraft.

A bug in the compiler can undermine even the most rigorous formal verification of source code. As an example, look at this code snippet on the right: a specific version of GCC shipped with Ubuntu Linux incorrectly compiled this simple comparison, returning 1 instead of 0 because it mishandled the promotion of signed and unsigned characters. This is a **"wrong-code" bug**, which is particularly dangerous because the compiler gives no warning; it simply produces a malfunctioning program.

## Slide 3

To solve this, the researchers used **Randomized Differential Testing**. The core idea is simple: if you have three or more compilers that are all supposed to follow the same C99 standard, you can feed them the same random program and compare their outputs. If one compiler produces a result that differs from the others, you have found a bug in either the minority compiler or the majority—either way, something is wrong. This approach is powerful because it doesn't require a manual "oracle" to know what the correct answer should be; the compilers provide the consensus themselves.

## Slide 4

However, for differential testing to work, **every generated program must have one, and only one, deterministic meaning**. This is the greatest technical challenge because the C standard is full of "gray areas": 191 types of **undefined behavior** (like signed integer overflow) and 52 types of **unspecified behavior** (like the order of argument evaluation).

If Csmith generated programs that triggered these, different compilers could produce different outputs legally, which would lead to "false positives". Csmith uses a **"checksum trick"** to identify bugs: the generated program prints a hash of its non-pointer global variables at the end of execution. If the checksum changes between compilers, it’s a bug.

## Slide 5

How does Csmith actually build these programs? It uses a **top-down, grammar-driven generation** process starting from the `main` function. It follows a six-step loop for every fragment of code:

1. It picks a production from a probability table.
2. It selects a target (like a variable or function).
3. It selects a type.
4. It recurses to generate sub-components.
5. It executes dataflow transfer functions to update its knowledge of the program state.
6. Finally, it performs a safety check. If the code is unsafe, it rolls back and tries again.

## Slide 6

**Safety** is managed through both code-generation-time and execution-time solutions. For example, to avoid **use-without-initialization**, Csmith uses explicit initializers. To prevent **out-of-bounds array access**, it uses bounded loop variables and modulo operators to force indices into a safe range. For complex problems like null-pointer dereferences or pointer lifetimes, Csmith performs a flow-sensitive, context-sensitive **pointer analysis** during generation to ensure no invalid pointer is ever used.

## Slide 7

The design of Csmith involves several **strategic trade-offs**. First, it allows **implementation-defined behavior**, such as integer widths, but handles this by testing compilers within "equivalence classes" (e.g., all 64-bit targets). Second, it doesn't guarantee **termination**; about 10% of programs might loop forever, which they handle with timeouts during testing. Most importantly, it specifically **targets the middle-end**, the optimization phases of the compiler, rather than just the front-end parser.

## Slide 8

Over three years, the team conducted **five major experiments**. They hunted for bugs opportunistically across 11 compilers, tracked the evolution of GCC and LLVM over time, and analyzed how program size and different generators impacted bug-finding power.

## Slide 9

The results were staggering. They reported **over 325 previously unknown bugs**. For GCC alone, 25 bugs were classified as **P1**, which is the highest "release-blocking" priority. They found that every compiler they tested—even those used for safety-critical embedded systems—contained bugs that could lead to silent miscompilation.

## Slide 10

In their quantitative comparison, they tested one million programs against various versions of GCC and LLVM. These logarithmic graphs show the **crash error rates**. While both compilers have generally improved, notice the spikes—new releases, like GCC 4.0.0, often introduced significant regressions in stability.

## Slide 11

These graphs also track the **wrong-code error rates** and internal consistency failures. The data reveals that while developers are good at fixing crashes, **wrong-code bugs**—the silent killers—remain a persistent and difficult challenge as compilers become more complex.

## Slide 12

An interesting finding was the relationship between **program size and bug-finding power**. The greatest number of distinct bugs was found in programs with **8,000 to 16,000 tokens**, averaging about 81 KB. Larger test cases are more effective because they trigger a combinatorial explosion of feature interactions that small, hand-written tests simply cannot reach.

## Slide 13

When compared to **prior random generators** like Randprog or DDT, Csmith is significantly more effective. In one week, Csmith found 86 distinct crashes, while older tools found far fewer. This is because Csmith generates much more expressive and "realistic-looking" code.

## Slide 14

The researchers also looked at **code coverage**. Surprisingly, adding 10,000 Csmith programs to the existing GCC or LLVM test suites barely moved the needle on traditional line or branch coverage. This suggests that our standard coverage metrics are too shallow; Csmith finds bugs not by hitting new lines of code, but by hitting new **paths and value combinations** within existing lines.

## Slide 15

So, where exactly are the bugs hiding? The vast majority are in the **Middle-end**—the machine-independent optimizers. GCC had 49 bugs in the middle-end and zero in the front-end. LLVM, being a younger compiler, had a more even distribution across its front-end, middle-end, and back-end.

## Slide 16

Let’s look at two specific examples. In **GCC**, a wrong-analysis bug in loop optimization caused the compiler to incorrectly identify a variable as loop-invariant, hoisting it out of the loop and changing the final result. In **LLVM**, a safety check error occurred when a simplification rule compared a value as "unsigned" instead of "signed," incorrectly concluding that an optimization was safe when it was not.

## Slide 17

To conclude, this research proves that **even mature, widely-used compilers are full of bugs**. Csmith has advanced the state of the art by generating complex, bug-triggering programs that are strictly well-defined.

The return on investment is clear: the researchers estimate it cost roughly **$1,000 per bug** found. Considering these compilers form the "trusted computing base" for nearly all software, that is a small price to pay for a more secure digital world.
